# 1. Project Overview

## 1.1 Introduction

The objective is to develop a dynamic personal portfolio website with an integrated admin dashboard.

The application will have two primary interfaces:

1. **Public Portfolio:** A website where visitors can explore personal information, technical skills, work experience, education, projects and contact information.
2. **Admin Dashboard:** A protected management interface where the portfolio owner can create, update, delete, publish and manage portfolio content without modifying frontend source code.

Both interfaces will operate within a single Next.js application and share the same backend and database.

## 1.2 Project Objectives

- Develop a professional personal portfolio.
- Create a secure admin authentication system.
- Manage portfolio information dynamically.
- Implement reusable UI components.
- Store portfolio data in a centralized database.
- Manage project images and other media.
- Receive and manage contact form submissions.
- Support draft and published content.
- Maintain a scalable and maintainable codebase.
- Deploy the application to a production environment.

## 2.1 Architectural Principles

- Use Server Components by default.
- Use Client Components only when browser interaction or client-side state is required.
- Keep database access on the server.
- Keep business logic outside page components.
- Use Zod for server-side input validation.
- Reuse shared UI components.
- Use one source of truth for portfolio data.
- Avoid unnecessary API layers.
- Protect every admin operation with server-side authorization.

Use PostgreSQL with Prisma ORM.

Reasons:

- Structured relational data.
- Strong TypeScript support through Prisma.
- Relationships between projects and technologies.
- Reliable transactions.
- Easier database migrations.
- Suitable for a portfolio CMS.

- Add indexes for frequently queried fields.
- Add appropriate unique constraints.
- Use transactions for related updates.
- Add audit fields if content history becomes necessary.
- Configure authentication adapter models if required by the selected Auth.js setup.
- Store only image URLs and provider identifiers in PostgreSQL, not image binary data.
- Consider a dedicated SocialLink model if social links need flexible ordering and multiple platforms.

# 8. Authentication and Authorization

## 8.1 Authentication Strategy

Use Auth.js for admin authentication.

Initial requirements:

- One admin account.
- Email/password credentials or another supported secure provider.
- No public registration.
- Secure session handling.
- Logout functionality.

For credentials-based authentication, store password hashes using a suitable password-hashing algorithm such as Argon2id or bcrypt. Never store plain-text passwords.

## 8.2 Authentication Flow

```text
Admin visits /admin
        |
Check existing session
        |
   +----+----+
   |         |
Valid       Invalid
   |         |
Dashboard   Login Page
   |         |
   |      Submit Credentials
   |         |
   |      Verify Password
   |         |
   |      Create Session
   |         |
   +----> Dashboard
```

## 8.3 Authorization Rules

Every protected server operation must:

1. Verify the session.
2. Confirm the user is authorized.
3. Validate incoming data.
4. Execute the business operation.
5. Return a safe result.

Do not rely only on middleware or frontend route hiding.

Server Actions must perform their own authorization checks because they can be invoked independently of the page UI.

## 8.4 Security Requirements

- No public registration.
- Password hashing.
- Secure HTTP-only session cookies.
- Production HTTPS.
- Server-side authorization.
- Login rate limiting.
- Input validation.
- Protection against unauthorized mutations.
- Secure environment variables.
- Safe error responses.
- Spam protection for contact forms.
- Regular dependency updates.

# 9. Backend Architecture

## 9.1 Service Layer

Each business feature should contain its own service file.

Example:

```text
features/projects/
├── projects.schema.ts
├── projects.service.ts
└── projects.types.ts
```

The service layer handles:

- Database queries.
- Business rules.
- Create operations.
- Update operations.
- Delete operations.
- Publishing rules.
- Data retrieval.

## 9.2 Server Actions

Server Actions are recommended for most admin CRUD mutations.

Example workflow:

```text
Project Form
     |
     v
Server Action
     |
     v
Authentication Check
     |
     v
Zod Validation
     |
     v
Project Service
     |
     v
Prisma
     |
     v
PostgreSQL
     |
     v
Revalidate Cached Data
```

Example conceptual Server Action:

```ts
"use server";

export async function createProject(input: unknown) {
  const session = await auth();

  if (!session?.user) {
    throw new Error("Unauthorized");
  }

  const validatedData = projectSchema.parse(input);

  return createProjectService(validatedData);
}
```

This is a simplified illustration. The production implementation should also verify admin permissions, handle errors safely and avoid trusting client-provided ownership or authorization fields.

## 9.3 Route Handlers

Use Route Handlers when required for:

- External API consumers.
- Webhooks.
- Integrations.
- File upload callbacks.
- Public endpoints.
- Services that need standard HTTP interfaces.

Avoid creating duplicate APIs for operations already handled cleanly through Server Actions.

# 11. Admin CRUD Workflow

Every management module should follow a consistent workflow.

## 11.1 Create

1. Admin opens the module.
2. Admin selects Add New.
3. Form opens.
4. Admin enters information.
5. Client-side validation provides immediate feedback.
6. Server Action validates again.
7. Service saves data through Prisma.
8. UI refreshes or revalidates the relevant data.
9. Success or error feedback is shown.

## 11.2 Read

- Display records in a table or card layout.
- Support search.
- Support filtering.
- Support pagination where necessary.
- Provide detail views when appropriate.

## 11.3 Update

- Load existing record.
- Populate the form.
- Validate modified values.
- Save changes.
- Refresh affected public and admin views.

## 11.4 Delete

- Display a confirmation dialog.
- Verify admin authorization.
- Perform the delete operation.
- Handle related records.
- Refresh the listing.

For important records, consider soft deletion or archival rather than permanent deletion.

# 22. Final Architectural Decisions

| Area | Decision |
|---|---|
| Application | Single Next.js application |
| Architecture | Feature-Based Modular Monolith |
| Public Interface | Next.js Server Components by default |
| Admin Interface | Protected Next.js routes |
| Database | PostgreSQL |
| ORM | Prisma |
| Authentication | Auth.js |
| Validation | Zod |
| Forms | React Hook Form |
| Mutations | Server Actions by default |
| External APIs | Route Handlers when required |
| Media | Cloudinary |
| UI | Tailwind CSS v4 + shadcn/ui |
| Deployment | Vercel |

## Final Recommendation

Build the portfolio and admin dashboard in the same repository and use a centralized database as the source of truth.

Do not start by building all admin screens. Establish the database and authentication foundation first, then implement the admin layout and individual content modules.

The first complete milestone should be:

1. Database connected.
2. Admin login working.
3. Protected admin dashboard accessible.
4. Profile information editable.
5. Updated profile automatically reflected on the public portfolio.

Once this workflow works end-to-end, use the same architecture for Skills, Experience, Education, Projects and Messages.

**The final goal is a maintainable personal portfolio CMS that allows the owner to manage the entire public portfolio from one secure admin dashboard without repeatedly changing frontend code.**
